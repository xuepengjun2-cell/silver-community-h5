# 历史原片保留 + 新小程序上传仅留交付版

当前小程序代码能保存图片和不超过 200 MB 的 MP4；它不会把 MOV 自动变成 MP4。抽查的真实相册有 36 个视频，其中 34 个 MOV、24 个大于 200 MB，因此转码不是优化项，而是正式上线的前置项。

1. **历史数据和 H5 上传不变。** 既有原片继续保留，历史 MOV/超大视频需要单独转码交付版；新小程序上传则以临时文件转码，成功后只将 MP4 交付版存到 TOS，不永久保存原片。两条流程不要混用。
2. **历史素材转码，尚未实现。** 服务端下载已存的 MOV/大视频到隔离临时工作区，转成 H.264/AAC MP4，`faststart`，实际小于 200 MB；检查格式、时长、大小和首尾可播放后再上传。视频过长或压缩后画质不可接受时，标记“需分段/人工处理”。
3. **历史素材交付字段，尚未实现。** 保留 `media.url`/`media.size` 原片，新增 `media.delivery = { url, size, sourceFingerprint, status }`；公开 API 仅返回 `ready` 的真实交付版。现有 `normalizeProjectMedia`/存储层会丢弃该字段，需要另行实施和回归。**新小程序上传**直接把转好的 MP4 写成 `media.url`，不采用此历史素材模型。
4. **权限与撤销。** 两条流程都应先通过云端与播放验证才对外发布；删除素材、下架相册、关闭分享都要阻断页面与保存接口。客户端保存前重新获取公开相册，再调用下载接口记数；已泄露的原始 CDN 地址不会因关闭分享自动失效，强撤销需另做签名分发。
5. **真机验收。** B 端发布 → 用小程序传 MOV/大 MP4 → 转码任务变 `ready` → 小程序卡片分享 → iPhone 微信保存到系统“照片” → 安卓/鸿蒙回归 → 后台下载统计；权限拒绝、断网、相册下架、转码失败都要可理解地提示。首批优先拿 1 个真实 MOV、1 个大于 200 MB 的 MP4 做验收，确认画质与算力成本，再考虑历史相册批量处理。

这份历史视频转码方案尚未在生产执行。新小程序上传管线已在开发分支编码，但未发布后端、未上传微信预览版，也未进行真实视频和照片真机验收；个人主体类目、域名和审核仍需账号持有人确认。

## 2026-09-22 存量素材只读核算与实施决策

- 已发布案例共 11 个、视频 544 个：490 个已是 MP4，54 个为 MOV。54 个 MOV 的 CDN `HEAD` 全部返回 200，合计约 0.96 GB，最大约 55 MB；案例接口中多数视频没有可靠的 `size` 字段，不能仅据数据库字段判断交付状态。
- 已发布活动 SOP 共 153 项，只有 4 条视频引用，其中 3 条无扩展名、1 条不是可直接解析的文件地址。它们不能按“已上传原视频”统一转码，须先确认来源、授权及可下载性。
- 抽查的一个已发布相册含 36 个视频：2 个 MP4、34 个 MOV。34 个 MOV 的已记录大小合计约 19.95 GB，最大约 1.44 GB，24 个超过当前小程序单文件 200 MB 的交付边界。该相册与上述案例视频 URL 没有重合；其他相册尚未完成逐一核算。
- 当前 `silver-new` 为 2 核、3.8 GiB 内存、约 6.1 GB 可用磁盘，PM2 `silver` 在线，已安装 FFmpeg。**不应在业务进程中并行批量转码或把所有源文件同时落盘**；优先使用隔离工作机/队列，或先验证单任务串行的资源余量。

结论：**可行，但不应把全部视频原址替换成 MP4，也不应重编码已有的 490 个 MP4。**先用 `ffprobe` 判定容器、视频编码和音频编码；可无损转封装的文件优先 remux，其余生成 H.264/AAC、`faststart` 的 MP4 交付版。每个交付版必须经时长、音画、首尾播放、CDN 可读、文件大小及手机真机保存验收后再标记 ready；不能达标的长视频需分段或人工处理。

实施顺序：先各选 1 个案例 MOV 和 1 个大体积相册 MOV 做小范围验证；再给相册和案例分别增加可追溯的交付版字段、幂等转码任务和失败重试；最后按需补处理历史 MOV 与不兼容 MP4。历史原件、原链接、案例下载鉴权、相册分享状态和下载统计都不改变。相册交付版用于客户保存，案例交付版用于其既有权限范围内的预览/下载；SOP 外部引用单独核验，不能纳入自动批处理。本轮只完成评估，**未启动历史转码、未修改生产媒体数据**。
