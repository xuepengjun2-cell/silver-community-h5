# 原片保留 + 微信相册交付版：上线必做

当前小程序代码能保存图片和不超过 200 MB 的 MP4；它不会把 MOV 自动变成 MP4。抽查的真实相册有 36 个视频，其中 34 个 MOV、24 个大于 200 MB，因此转码不是优化项，而是正式上线的前置项。

1. **B 端上传不变。** 原片仍按原流程进入 TOS，作为主办方的原始资产；异步任务收到项目 ID、素材索引、原片对象键和大小，不能把长时效云存储密钥放入小程序。
2. **生成交付版。** 服务端下载原片到隔离的临时工作区，转成 H.264/AAC MP4，`faststart`，以约 190 MB 为输出目标留余量；检查格式、时长、实际文件大小和首尾可播放后再上传。视频过长、压到目标大小会明显糊掉时，标记“需分段/人工处理”，不能谎报成功。
3. **按原片指纹幂等入库。** 保留 `media.url`/`media.size` 原片信息，新增 `media.delivery = { url, size, sourceFingerprint, status }`，通过原片指纹、转码参数和唯一对象键防止重复付费/重复写入。公开 API 仅返回 `status=ready` 的真实交付版，不暴露内部错误或密钥。现有 `normalizeProjectMedia`/存储层目前会丢弃 `delivery` 字段，后端改动时必须同时更新归一化、持久化及回归测试。
4. **数据与权限一致。** 生成交付版后，先完成 TOS/CDN HEAD 和播放验证，再把 `ready` 写入项目；删除素材、下架相册、关闭分享都要阻断页面与保存接口。客户端保存前重新 GET 公开项目，再调用原有下载接口记数；若要求“转发出去的原始 CDN 地址也立刻失效”，需另做同域签名分发，不能仅靠隐藏页面。
5. **真机验收。** B 端发布 → 传 MOV/大 MP4 → 转码状态变 `ready` → 小程序卡片分享 → iPhone 微信保存到系统“照片” → 安卓/鸿蒙回归 → 后台下载统计；权限拒绝、断网、相册下架、转码失败都要可理解地提示。首批优先拿 1 个真实 MOV、1 个大于 200 MB 的 MP4 做验收，确认画质与算力成本，再考虑历史相册批量处理。

这份方案没有启动线上批量转码、修改现有服务端或支付任何云服务费用。AppID 已填入开发工程；个人主体的认证状态、类目审核与域名配置仍需账号持有人确认后才能进入真机验收。
