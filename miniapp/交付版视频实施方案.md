# 历史原片保留 + 新小程序上传仅留交付版

当前小程序代码能保存图片和不超过 200 MB 的 MP4；它不会把 MOV 自动变成 MP4。抽查的真实相册有 36 个视频，其中 34 个 MOV、24 个大于 200 MB，因此转码不是优化项，而是正式上线的前置项。

1. **历史数据不变。** 既有原片继续保留，历史 MOV/超大视频需要单独转码交付版；新小程序上传则以临时文件转码，成功后只将 MP4 交付版存到 TOS，不永久保存原片。H5 新上传另有受控开关，见本文末节；历史与新上传不要混用。
2. **历史素材转码，尚未实现。** 服务端下载已存的 MOV/大视频到隔离临时工作区，转成 H.264/AAC MP4，`faststart`，实际小于 200 MB；检查格式、时长、大小和首尾可播放后再上传。视频过长或压缩后画质不可接受时，标记“需分段/人工处理”。
3. **历史素材交付字段，尚未实现。** 保留 `media.url`/`media.size` 原片，新增 `media.delivery = { url, size, sourceFingerprint, status }`；公开 API 仅返回 `ready` 的真实交付版。现有 `normalizeProjectMedia`/存储层会丢弃该字段，需要另行实施和回归。**新小程序上传**直接把转好的 MP4 写成 `media.url`，不采用此历史素材模型。
4. **权限与撤销。** 两条流程都应先通过云端与播放验证才对外发布；删除素材、下架相册、关闭分享都要阻断页面与保存接口。客户端保存前重新获取公开相册，再调用下载接口记数；已泄露的原始 CDN 地址不会因关闭分享自动失效，强撤销需另做签名分发。
5. **真机验收。** B 端发布 → 用小程序传 MOV/大 MP4 → 转码任务变 `ready` → 小程序卡片分享 → iPhone 微信保存到系统“照片” → 安卓/鸿蒙回归 → 后台下载统计；权限拒绝、断网、相册下架、转码失败都要可理解地提示。首批优先拿 1 个真实 MOV、1 个大于 200 MB 的 MP4 做验收，确认画质与算力成本，再考虑历史相册批量处理。

绍兴相册已单独完成历史转码（2026-09-22，36 个视频均替换为带首帧的 MP4；一次性迁移接口与脚本已于 2026-09-25 移除），其他相册尚未执行（2026-09-25 核对：另两个相册共 23 个视频无首帧、4 个超过 200 MB）。新小程序上传管线的后端已于 2026-09-22 部署；截至 2026-09-22 未上传微信预览版，也未进行真实视频和照片真机验收；个人主体类目、域名和审核仍需账号持有人确认。

## 2026-09-22 存量素材只读核算与实施决策

- 已发布案例共 11 个、视频 544 个：490 个已是 MP4，54 个为 MOV。54 个 MOV 的 CDN `HEAD` 全部返回 200，合计 957,671,100 字节（约 958 MB）；最小 256,553 字节（约 0.26 MB、时长仅 0.13 秒，`video_1785298221366-29d272a6.mov`），最大 55,390,791 字节（约 55.39 MB、时长 31.27 秒，`video_1785298221542-f307272b.mov`）。这两个文件都属于“绽放吧姐姐-北京老年春晚海选”；最短片段是否有业务价值，应在历史迁移前人工确认。案例接口中多数视频没有可靠的 `size` 字段，不能仅据数据库字段判断交付状态。
- 已发布活动 SOP 共 153 项，只有 4 条视频引用，其中 3 条无扩展名、1 条不是可直接解析的文件地址。它们不能按“已上传原视频”统一转码，须先确认来源、授权及可下载性。
- 抽查的一个已发布相册含 36 个视频：2 个 MP4、34 个 MOV。34 个 MOV 的已记录大小合计约 19.95 GB，最大约 1.44 GB，24 个超过当前小程序单文件 200 MB 的交付边界。该相册与上述案例视频 URL 没有重合；其他相册尚未完成逐一核算。
- 当前 `silver-new` 为 2 核、3.8 GiB 内存、约 6.1 GB 可用磁盘，PM2 `silver` 在线，已安装 FFmpeg。**不应在业务进程中并行批量转码或把所有源文件同时落盘**；优先使用隔离工作机/队列，或先验证单任务串行的资源余量。

结论：**可行，但不应把全部视频原址替换成 MP4，也不应重编码已有的 490 个 MP4。**先用 `ffprobe` 判定容器、视频编码和音频编码；可无损转封装的文件优先 remux，其余生成 H.264/AAC、`faststart` 的 MP4 交付版。每个交付版必须经时长、音画、首尾播放、CDN 可读、文件大小及手机真机保存验收后再标记 ready；不能达标的长视频需分段或人工处理。

历史素材实施顺序：先各选 1 个案例 MOV 和 1 个大体积相册 MOV 做小范围验证；再给相册和案例分别增加可追溯的交付版字段、幂等转码任务和失败重试；最后按需补处理历史 MOV 与不兼容 MP4。历史原件、原链接、案例下载鉴权、相册分享状态和下载统计都不改变。相册交付版用于客户保存，案例交付版用于其既有权限范围内的预览/下载；SOP 外部引用单独核验，不能纳入自动批处理。**未启动历史转码、未修改生产媒体数据**。

## 2026-09-22 H5 新上传后台压缩实现（已于 2026-09-22 部署到生产）

- 开关 `H5_AUTO_VIDEO_DELIVERY` 默认开启（未设置即接管 H5 新上传），仅在紧急回退时设为 `0`。案例后台仍接受原视频文件，≤300 MB；服务端单队列探测视频，兼容 H.264/AAC 的优先无损转封装，其余压缩到 720p / 25 fps、H.264/AAC、`faststart` MP4，最终须小于 190 MB。转码成功且 TOS 对象大小校验通过后才向编辑器返回 URL；失败不发布，临时原片清除并提示重传。
- 活动相册 H5 视频（≤2 GB）统一分片直传 TOS，合并后状态先为 `processing`，不立刻进入公开相册。后台单队列下载暂存原片、生成 MP4、校验后才写入相册；成功后删除**本次新上传**的 TOS 原片以节省长期空间。失败状态为 `delivery_failed`，原片留在 TOS，可用同一上传会话重试转码；页面重选同一文件会恢复任务，不重新传 2 GB。任务重启可从数据库会话恢复，处理前检查临时磁盘余量。
- 生产节点仅 2 核，磁盘余量有限（2026-09-25 核对约 5.4 GB 可用、已用 89%），且与学习中台服务共用；9/23 已有 39 个案例视频经此链路转码成功，但尚未做真实大视频的耗时、画质、TOS/前端完整联调。仍需用 1 个案例 MOV 与 1 个大相册 MOV 补做受控验收，并检查原片删除、失败重试、匿名分享保存和案例下载鉴权；出现 CPU 或磁盘压力时用 `H5_AUTO_VIDEO_DELIVERY=0` 回退；单个超 40 分钟或无法压到 <190 MB 的视频需要分段，不承诺无限长原视频自动可交付。
- 视频号采集器的独立案例直传接口仍按原流程保留原片；本次不改该自动化链路。照片、GIF/SVG、SOP 外部视频引用也未纳入本次 H5 视频压缩。现网已默认压缩 H5 新上传的相册与案例视频（见上）。
- 使用上述最大的 31 秒案例 MOV 在现网主机**临时目录**做一次不入库、不上传 TOS 的编码样本：55,390,791 字节 → 9,425,906 字节（约缩小 83%），31.271667 秒 → 31.28 秒，输出为 1280×720、H.264/AAC。临时源文件和输出文件已清理。此项只验证编码和体积，尚未人工验收面部画质、快速运动画面、云端交付以及手机真机保存。
